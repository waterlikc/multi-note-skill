来源材料

01为什么需要握手

TCP 是可靠、面向连接的协议。连接建立前，双方要确认两件事：彼此都能发送、都能接收，并同步各自的初始序列号。

提示

握手不是“打个招呼”，而是在不可靠的网络上建立可用的双向通道。

补充解释

02三次报文：SYN → SYN+ACK → ACK

三个报文各自携带序列号；第三次 ACK 让服务器确认“客户端确实收到了我的 SYN+ACK”。

下一节：为什么两次不够 →

补充解释

04为什么两次不够

  • 两次只能确认：客户端能发、服务器能收；以及服务器能发、客户端能收（但服务器不知道客户端收到了）。
  • 第三次 ACK 让服务器确认客户端的接收能力，也避免旧 SYN 造成错误连接。
  • 两次握手无法让服务器区分“新连接”与“延迟到达的旧 SYN”。
提示

核心不是“多一次更保险”，而是第三次才让服务器获得“客户端已收到”的证据。

05丢包与重传

丢失的报文客户端服务器结果
SYN重传 SYN看不到连接超时后重试
SYN+ACK重传 SYNSYN-RCVD 等待服务器超时回收
ACKESTABLISHEDSYN-RCVD服务器重传 SYN+ACK

握手阶段的重传由内核定时器处理；应用层看到的是连接建立变慢或失败，而不是“报文一定丢了一次”。

下一节：安全边界：SYN Flood 与半连接 →

补充解释

07安全边界：SYN Flood 与半连接

服务器收到 SYN 后要分配半连接资源；大量伪造源地址的 SYN 会占满 SYN 队列，这就是 SYN Flood 的资源耗尽路径。

  • SYN Cookie 把状态编码进序列号，减少半连接存储。
  • 限速、代理、清洗设备只能缓解，不改变握手语义。
  • 不要用“握手成功”推断对端身份可信。
